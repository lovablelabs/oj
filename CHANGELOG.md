## [Unreleased]

### Fixed

- `oj build`: an asset in the bundle `generateBundle` and `writeBundle` receive carries `originalFileNames` and `originalFileName`, as Rollup's `OutputAsset` does: the source paths the asset was emitted for (root-relative for an imported file, as Vite's asset plugin emits them), an empty array and `null` when there are none. oj passed `name`, `names` and `source` alone, so a plugin reading the field as the type allows, `output.originalFileNames.some((file) => ...)` in a guard over what a build ships, failed the build with `Cannot read properties of undefined (reading 'some')` where `vite build` passed. The `.vite/manifest.json` asset a plugin sees has the same shape.
- The plugin host's JS heap is sized as Node sizes its own: by V8, from the memory the process may use (the machine's, or the cgroup ceiling when that is lower), which is also how Deno's CLI does it. oj capped the whole heap at a fixed 4096 MB, young and old generation together, where V8 gives the old space half the memory up to 4096 MB and puts the young generation on top: 4192 MB from 8 GB of memory up with oj's V8, so a plugin hook that just fit under `vite build` could fail under oj with `plugin host exceeded its memory limit`, and on a machine with less memory the cap was more than V8 would allow there (1072 MB at 2 GB, 2144 MB at 4 GB). `--max-old-space-size=N` in `NODE_OPTIONS` sizes the old space as it does for Node, the young generation above it. `OJ_PLUGIN_MEMORY_MB` is removed: `NODE_OPTIONS=--max-old-space-size=<MB>` is the one way to set the cap, as under Vite, and the memory-limit error names it.
- TanStack Start dev: `oj dev` on an app whose modules import one another (a `lib/` directory of helpers that use each other, a chain of modules each re-exporting the next's bindings) starts, where it printed `server-fn resolver cache miss` and then sat at a full core for minutes without binding its port, and `oj build` scanned the same tree the same way. The server-function finder follows an import to the module that exports the binding, as Start's compiler does (`resolveImportKind`), but it read that module anew for every name imported from it and for every path the imports reached it by, each read resolving the module's own imports the same way: the walk visited every simple path through the import graph, exponentially many, before it answered for the first file. The finder now reads each module once per resolution and resolves a binding when a chain names it, memoizing the result, as the compiler's `moduleCache` and `resolvedKind` do, so the time a scan takes grows with the modules reached. With a binding resolved where it is named, a variable holding the factory (`const make = createServerFn; export const x = make().handler(..)`) is the factory in its own module too, as it already was through an import, as the compiler's `resolveIdentifierKind` reads it. What a module exports under a name is searched as the compiler's `findExportInModule` searches it: the module's own export, then its `export *` modules in order, each module looked at once in a search and every search starting anew, the first module that exports the name answering whatever the name is bound to there. So with `m` re-exporting all of `n` and `o` and `n` all of `m`, a builder `o` declares is found through `n` as through `m`, in whichever order a file imports them, and modules that each re-export all of the others are looked at once each. Only a chain ending in `.handler(..)` has its root resolved, so a `z.object(..)` or `db.query()` in a server-function file reads no module and builds no resolver.
- TanStack Start: a server function finished on a builder another module exports (`export const authedFn = createServerFn().middleware([auth])`, then `authedFn.handler(..)` in a `*.functions.ts` module) is found when the import is spelled through a tsconfig `paths` alias (`import { authedFn } from "@app/lib/authed"`), through the package.json `imports` map (`#lib/authed`), or as the module's default export (`import authedFn from "./authed"`, `export default authedFn` there). oj followed a relative specifier and a named export alone, so a chain rooted at a builder imported any other way was no server function to it: the client bundle kept the handler, and Start's import protection denied the `*.server.*` module (or `@tanstack/react-start/server`) only the handler used, in dev (no page hydrated) and in the build, while the same app built under Vite, whose Start compiler resolves the import with `this.resolve` and reads the module's `default` export like any other (`resolveImportKind`, `findExportInModule`). The finder now resolves a non-relative specifier with the app's resolver (the tsconfig that owns the importer applying its `paths`, as Vite 8's own resolver does, and Node's `imports` map), a file under the app's root and outside `node_modules` counting as the app's, and reads `export default` for a default import, on every side that must agree on the ids: the client rewrite, the server rewrite and the server-fn resolver's scan.
- TanStack Start: a namespace import of one of the app's modules names what the module exports, the factory included (`import * as kit from "@app/lib/kit"`, `export { createServerFn } from "@tanstack/react-start"` there, then `kit.createServerFn().handler(..)`), as Start's compiler resolves a namespace's member as an import of that name (`resolveCalleeKind`): a relative namespace's member was never the factory, and the handler stayed in the client. A module's own `export default` is its default though an `export *` is written before it, as the compiler's `findExportInModule` reads the module's export map first.
- TanStack Start dev: the server-fn resolver cached under `.oj-cache` is regenerated when any source file, a tsconfig or package.json changed, and in a running dev server when an edit touches a module the last scan read for an imported builder (the builder's module, a barrel re-exporting it). It was keyed on the files naming `createServerFn` alone, so a server function added to a file whose builder is imported (`authedFn.handler(..)`, no `createServerFn` in the file) restored the old resolver, across restarts too, and the client called an id the server answered with `Server function info not found`. The key also covers what the scan read that is not a `.ts`/`.tsx` file under `src/` (a `.js` builder, a module of a directory an alias names), a file created where an import found none (a new barrel, the target of an alias) or that takes the place of the one read (`barrel.js` beside `barrel.ts`), the tsconfig files under `src/` and the files a tsconfig names by a relative `extends` or `references` path; a cache written by an earlier oj, whose memo recorded which files named `createServerFn`, no longer keeps the others out of the key, and a cached resolver is restored only when the modules it lists as read are the ones the key was made with.

## [0.4.13] - 2026-11-11

### Changed

- rolldown 1.3.2 (from 1.3.0) and oxc 0.158 (from 0.157), which 1.3.2 requires. `oj build` output still matches `vite build` byte for byte on the parity apps. What reaches oj from rolldown 1.3.1 and 1.3.2 is bundler fixes and speedups: a build fails instead of hanging when a module task panics, a partial dev rebuild that adds a relative-path external no longer panics, `var` is hoisted out of top-level `catch`, `for-in` and `for-of` heads of wrapped modules, top-level `await` in a top-level `catch` block is detected, a module without module syntax that is both imported and required is CommonJS, cross-chunk export names no longer depend on module load order, statements made dead by imported constants are dropped before chunk linking, and incremental rebuilds reuse link-time facade symbols and share sourcemap chains.

### Fixed

- Dev server: a dependency installed after the server started and imported through `await import("pkg")` in a handler loads, where the import rejected with "Failed to fetch dynamically imported module" (a 504) a moment before the page reloaded; a second click after the reload worked. The edit that imports the new package registers it for re-optimization and rewrites the import to its future pre-bundle, whose request waits for the rerun to commit. When that rerun moves a pre-bundled chunk the page already loaded (a React page's pre-bundles share their runtime chunk), the commit gives every entry a new version and reloads the page, and oj compared the waiting request's version against the new one and answered it outdated. Vite's `optimizedDeps` load hook checks the request's version against the entry's when the request arrives, and after the await compares the discovered entry's info, which its commit updates in place, with the committed one, so a request held across the commit is served the bundle it waited for and the reload follows; the dep route now does the same. A request that arrives after the commit under the old version is still Vite's outdated 504, which the reload retries.
- TanStack Start dev: a change that adds an export to a module and reads it from a component importing that module (an `export const visibleConcerts` in a data module, mapped over in the component, written as two files) reaches an open page as one hot update. The two writes are two patches, one per file; the page applied each as it came, so the component's patch re-ran the component against the data module's exports from before the edit: the new export was `undefined`, the render threw on it (into the router's error component, or unmounting the page without an error boundary), and the data module's patch, applied next, had nothing left to refresh, while a fresh load rendered fine. A page close to its server rarely saw it (the refresh runtime waits 16ms before it re-renders, and the second patch usually landed first); one far from its server, where fetching a patch takes longer, saw it on most such changes, the editor's gate releasing both patches together making no difference. The page now fetches every patch it has been sent, those released together and any that arrive while it fetches, before it re-runs a module, then re-runs the changed modules once over all of them, so each importer binds to the newest exports, as under Vite, whose module graph invalidates every changed file as the watcher reports it (`onFileChange`) and whose boundary re-import then loads each import fresh.
- Dev server: Vite's URL for a pre-bundled dependency, `/node_modules/.vite/deps/react.js` (`react-dom_client.js` for `react-dom/client`, `@tanstack_react-query.js` for `@tanstack/react-query`: the optimizer's `flattenId`), is served, where oj answered 404 and knew its pre-bundles by `/@oj-deps/<file>?v=<version>` alone. A script or a retained test written against Vite's cache paths, or tooling that drives the page with them, loads the dependency the app itself runs on: an import of the Vite URL in a served module is rewritten to the pre-bundle's own URL, as the bare import is, and a request for the URL itself (a dynamic import from outside oj's transform) gets a module re-exporting that pre-bundle, so the page keeps one instance of each dependency however the import was spelled. Serving the bundle's bytes under the second URL, or redirecting to the first, would have evaluated it twice, the second React or QueryClient some worked around the 404 with by importing an `/@oj-deps/` URL by hand. A CommonJS dependency's names come with it (`createRoot` from `react-dom_client.js`), as Vite's import analysis gives them to an importer of its optimized file. A stem that names an installed dependency nothing has imported yet registers it with the optimizer, as a bare import would (Vite's `registerMissingImport`), and the request waits for the re-optimization; one that is not a dependency is a 404, as Vite's optimized-deps plugin answers a file missing from its cache dir, and one whose re-optimization fails is Vite's processing error, a 504. The URL follows the config's `cacheDir` as Vite resolves it: `/.cache/vite/deps/` for `cacheDir: ".cache/vite"`, else `node_modules/.vite` under the nearest package.json at or above the root, which for a root inside a package is the `/@fs/` form of that directory. Vite's `?v=` hash on such a URL is Vite's and is ignored.
- TanStack Start dev: an edit saved while the server is still warming its engine after boot (the first seconds, longer on a slow machine or a cold cache) reloads the page once, when its rebuild ends. The boot's revalidation, which drops the modules edited while the engine warmed, counted a reload for them too, and the watcher's rebuild for the same edit counted its own: without the editor's HMR gate the page reloaded twice, and under the gate a flush that landed while the rebuild ran published the revalidation's reload first, onto the bundle from before the edit, with the rebuild's reload following; and while the watcher thread was still scanning the app (seconds on a slow disk), the edit queued on its feed behind the scan, the revalidation's reload went out past the gate, before any hold was taken. The revalidation now leaves the reload to the watcher's rebuild whenever the watcher is going to see the edit, decided by waiting until the watcher has read its feed, and reloads itself only for an edit no watcher run covers; and a flush that lands while a rebuild runs waits for that run, whose end releases the held reloads and hot updates once, onto its output, as a flush between rebuilds always did.
- TanStack Start dev: the script tag oj appends to a server-rendered document (its live-reload client) carries the document's CSP nonce. An app under a strict policy (`Content-Security-Policy: script-src 'nonce-..' 'strict-dynamic'`, the nonce handed to Start as the request context and the router's `ssr.nonce`) had every tag Start rendered nonced and oj's alone not, so the browser refused it: no reload on an edit, no build-error overlay, and a policy violation in the console on every page. Under Vite no tag of its own reaches a Start document (its client arrives as an import of the nonced client entry), and the tags Vite injects into a page take `html.cspNonce` (plugins/html.ts `injectNonceAttributeTagHook`). oj's tag now takes the nonce the document's own `<script>` tags carry, read off the body as it streams (Start's `<Scripts>` writes the router's nonce double-quoted, router-core's `injectScript` single-quoted; a tag split across two chunks is read whole), which is the nonce the request's policy header names, else `html.cspNonce` when the config sets it. A document whose tags have no nonce gets a tag without one, and the app's own tags are never given one, as Vite leaves a Start document's tags alone. The stylesheet links the live-reload client adds for a hot update's new CSS carry a nonce too, the one Vite's client reads for the tags it creates (`<meta property="csp-nonce">`, client.ts `updateStyle`), else the nonce of oj's own tag, so a `style-src` policy that names a nonce accepts them.
- TanStack Start dev: a page open across many rebundles keeps loading its chunks. A rebundle renames every chunk whose content changed, and a document served before it imports a route's chunk lazily by the old name when the user first navigates there; the dev server kept the chunks of the last seven bundles behind the current one (the bundle store's window on disk), so a page behind by more, its reload held for the editor's flush while the edits kept coming, or on a hot session, where the pages never reload and every pause in typing rebundles, got a 404 and went blank ("Importing a module script failed" in Safari, "Failed to fetch dynamically imported module" in Chrome) until a hard reload; and a bundle the store could not cache lost its chunk files to the next rebundle at once, since the bundler emptied the chunks directory before writing. The chunks directory is the dev server's now: every bundle's chunk files stay in it for as long as the server retains that bundle, a window that is a budget on disk (256 MiB of chunks beyond the current bundle's, at most 64 bundles) rather than a count the store sets, and a bundle's files leave when it falls out of the window and no served bundle names them. A bundle restored from the store at boot has its chunks linked in; what an earlier run left is removed. Vite's bundled dev keeps every output of the session in memory for the same reason (server/bundledDev.ts `storeOutputFiles` never clears `memoryFiles`).
- Dev server: a plugin's `configureServer` middleware mounted on a route (`server.middlewares.use("/api", handler)`) runs as it does on Vite's connect stack: the route matches the request path case-insensitively and only at a segment boundary (`/api` takes `/api/users` and `/api.json`, not `/apiary`), the handler reads `req.url` with the route stripped (`/users?page=2`) and the browser's url in `req.originalUrl`, and the url is whole again for the middlewares after it, spelled with the route as mounted. oj matched the route as a plain, case-sensitive prefix and handed the handler the full url with no `originalUrl`, so a handler written for connect (one that routes on `req.url` past its mount point, or reads `req.originalUrl`) took the wrong branch. Every middleware now sees `req.originalUrl`, which changes what some do under a non-root `base`: `@cloudflare/vite-plugin`'s worker dispatch, for one, serves `req.originalUrl` when it is set, so its worker gets the browser's url with the base, as under Vite, where it got the stripped one. The stack's other connect shapes hold too: `server.middlewares.stack` entries carry the route as mounted (the empty string for the root, which plugins that splice their own entry in read), `use(route, app)` takes a sub-app with a `handle` and an `http.Server`, and an absolute-form url (`http://host/path`, the form a plugin's own bridge may call the stack with) matches on its path and keeps its scheme and host. Found while looking into a report of `vite-plugin-static-copy`'s copied files answering 404 under `oj dev`, which reproduces under a non-root `base` alone: the plugin moves its middleware ahead of Vite's `viteServePublicMiddleware` in `server.middlewares.stack`, which sits after Vite's base strip, and oj's stack had no entry of that name, so the plugin's splice landed its middleware before the strip, where it looked the file up with the base still on and missed. The stack now carries Vite's `viteServePublicMiddleware` and `viteTransformMiddleware` by name (they only pass; oj serves those requests itself), so a plugin's splice lands where it does under Vite. At the root base the plugin worked: its file map is built in `buildStart`, which oj awaits before serving, as under Vite; tests hold both shapes.
- Dev server: vite-plugin-svgr configured for every `.svg` (`svgr({ include: "**/*.svg", svgrOptions: { exportType: "named", namedExport: "ReactComponent" } })`, the CRA convention, or the same `include` with the default export) makes a plain `import { ReactComponent as Logo } from "./logo.svg"` the component in dev, as it did in `oj build` and under `vite dev`. oj routed a plain svg through the plugins only when one had a `transform` hook, and vite-plugin-svgr works in `load`; with `@vitejs/plugin-react` done natively the plugin was the only active one, so every plain svg import was rewritten to `?url` and served as its URL module, and the page failed on the missing `ReactComponent` export. Vite offers each plugin's `load` before `vite:asset`'s, which answers the URL only for a file no plugin claimed (plugins/asset.ts `load`), so a `load` hook now makes a plain svg a candidate as a `transform` did; one the plugin's filter does not match is still its URL, stored under the file's key like any module so the next request for the unchanged file is the warm path (one stat, a real ETag) rather than the hooks again, and a `load` hook is asked only as Vite's container would ask it: not when its own filter cannot match the svg's id (a virtual-module plugin's), and not when Vite runs it after `vite:asset` (a normal or `post` plugin's, unless the hook has `order: "pre"`), whose URL module answers a plain svg first; a `pre` plugin's function-form `load` (lovable-tagger's) is offered the id once, as under Vite. The plain svg import now carries Vite's `?t=` stamp after an edit, as a `?url` import did, so the page loads the edited module rather than the one its module map holds. A BOM-prefixed svg counts as markup too (the BOM is no Unicode white space, so the check for the `<` missed it). With the plugin at its default `include` (`**/*.svg?react`), `import Logo from "./logo.svg?react"` is the plugin's component: oj's own `?react` svgr wrapped the component the plugin had already made and the module failed to parse (500).

## [0.4.12] - 2026-11-11

### Added

- `oj lint`: the project's oxlint with oj as the backend for its type-aware rules. oxlint hands the rules that need types (`typescript/no-floating-promises` and the rest of tsgolint's) to a backend process, tsgolint by default; oj now carries tsrs's port of those rules (`tsrs_lint`, vendored as `oj_tsrs_lint`) on the checker `oj typecheck` runs. `oj lint` takes oxlint's arguments, runs the project's `node_modules/.bin/oxlint` (or the one `OJ_OXLINT_PATH` names) with `--type-aware` and `OXLINT_TSGOLINT_PATH` set to oj, and exits as oxlint does. A project that runs oxlint itself can set `OXLINT_TSGOLINT_PATH` to the oj binary for the same backend.

### Changed

- `oj typecheck` and the dev server's checker run on tsrs 0.24.0 (from 0.21.0), still TypeScript 7.1.0-beta on the same TypeScript source pin. What reaches oj from those releases: the parser no longer panics on a JSDoc comment whose indentation splits Unicode whitespace (0.24.0). `oj typecheck --watch` runs the reworked program reuse: after an edit that keeps a file's imports the program is reused, as before, and a file with a synthetic import (the JSX runtime, `tslib`) now owns the nodes reused for it; its reports are unchanged. The checker's other changes are behind tsrs's opt-in fast preset (`--fast`, `TSRS_FAST=1`), most of the rest is its language server, which oj does not use, and the releases' type-aware lint work for oxlint (`tsrs_lint`) is not vendored.

### Fixed

- TanStack Start dev: `import recipe from "./recipe.json" with { type: "json" }` in a module the server renders no longer fails every page with "Cannot resolve module ./recipe.json" (500). The SSR compile kept the attribute, which the runner honours: it asked for a JSON module and the JavaScript module oj serves for a JSON file (`export default {...}` plus named exports, as Vite's json plugin) was no match. Vite's ssrTransform replaces each static import with a `__vite_ssr_import__` call, so no attribute reaches its module runner; oj's SSR compile now drops a static import's or re-export's attributes as its dev server has since 0.4.3, and a dynamic import keeps its options, which the runner does not read (Vite's `__vite_ssr_dynamic_import__` takes the specifier alone), so `await import("./recipe.json", { with: { type: "json" } })` loads the same module. A dependency that imports its own JSON with the attribute (an ES module package under `node_modules`, where Node requires it) renders too: Vite externalizes the package and Node loads the file as a JSON module, so oj's runtime now does, where the host answered every dependency JSON with the json plugin's JavaScript module, no match for the JSON module the import asks for. Node requires the attribute for JSON, so the source could not drop it.

## [0.4.11] - 2026-11-11

### Fixed

- TanStack Start: a server function is found wherever Start's compiler finds one, not only in `export const name = createServerFn()...`: a type-annotated declaration (`export const plan: Plan = createServerFn(..)`), a `let` or `var`, the factory imported under another name (`import { createServerFn as fn }`) or called as a namespace import's member (`start.createServerFn()`), a chain through a variable holding the factory (`const base = createServerFn(); export const x = base.handler(..)`), a chain through a builder another module exports (`import { base } from "./base"`, followed through its re-exports as the compiler's `resolveImportKind` does, with the module read for the `.handler(` call alone as Start's detection does), and TypeScript's `as`, `satisfies` and `!` around the chain. oj decided it textually, from `const NAME = createServerFn`, so a function declared otherwise kept its handler in the client bundle, where import protection denied the `*.server.*` module (or `@tanstack/react-start/server`) the handler loaded, in dev and in the build, and the function went unregistered on the server. The finder now reads the module's AST as Start's `start-compiler` does (a module variable whose initializer ends in `.handler(..)` on a chain rooted at the factory, resolved through the module's bindings). As in Start, a `.handler(..)` call that is not a variable's initializer (an object literal's property, a `return`) is not a server function.
- TanStack Start dev: a response body streams to the client as the handler writes it. A server route answering with a `ReadableStream` (server-sent events written every second, a chunked download) or a render's deferred content reached the browser in one burst once the handler closed the stream, where under Vite's dev middleware each chunk arrives as written (the Start plugin hands the Response to srvx's `sendNodeResponse`, one `res.write` per chunk). oj's in-process runner read the whole body before replying; it now replies as soon as the handler's Response resolves and pulls the body chunk by chunk, each going out as it comes, and a client that leaves cancels the stream in the runner. A body holds the runner that produced it, not the engine's lock: a long-lived event feed never holds up the runner's respawn after many reloads (nor the requests behind it), and a feed open across a respawn finishes on the runner that started it. `OJ_START_RESPAWN_STALE` sets how many stale module instances a respawn waits for.
- Dev server: a file under `publicDir` imported by its url (`import logo from "/assets/logo.png"` for `public/assets/logo.png`) is a module exporting that url, as Vite serves it: its import analysis marks such an import as a module request (`?import`), its public middleware steps aside for one (`isImportRequest`) and `vite:asset` answers with the url (`checkPublicFile`, `fileToDevUrl`). oj left the import as written and served the url as the file, so the browser got `image/png` for a module script, the whole module graph failed and the page stayed empty. The import is now marked `?url`, as a relative asset import is, and a request for a public asset that asks for the module (`?import`, `?url`, or the browser's `Sec-Fetch-Dest: script`) gets `export default "/assets/logo.png"`; the bare url is still the file, and a public script or stylesheet is always the file. An import of a public file that is not an asset (a script, a stylesheet, a JSON file) fails the importer with Vite's error, word for word ("Cannot import non-asset file /data.json which is inside /public. ... use /data.json?url instead."), where it was left as written for the browser to fail on its MIME type; `?url` on it is its url, as the message says.
- TanStack Start: a middleware made from the app's Start instance (`startInstance.createMiddleware().server(...)`, the typed `createMiddleware` that `createStart` returns) compiles for the client like one made from the `createMiddleware` factory: its `.server(..)` link leaves the client, and with it what only the server half used (an `await import()` of a `*.server.ts` module, an import of `@tanstack/react-start/server`). Start's compiler resolves the member call through the binding to `createStart`; oj's knew the factory by its imported name only, so the server half shipped to the browser and import protection denied its import there, in dev and in the build. The instance is found in the module itself (`const startInstance = createStart(..)`) or through its import, following re-exports as the factories already were. It is found by its binding rather than by how the chain is written, as Start's compiler does: a chain a formatter broke before `.createMiddleware`, parentheses and TypeScript's `as` / `satisfies` / `!` around the instance or the `createStart(..)` call, a variable aliasing the instance, a call on `createStart(..)` itself, and a `createStart` the app re-exports from a module of its own. A middleware kept in a variable or chained under those wrappers (`const base = createMiddleware() as any`, `base!.server(..)`) is followed the same way, for the factory too, and an optional chain (`startInstance?.createMiddleware()`), no candidate of Start's compiler, is left as written.
- TanStack Start: an app's own server entry written as the package documents it, `import handler, { createServerEntry } from "@tanstack/react-start/server-entry"` and `export default createServerEntry({ fetch })`, serves in dev and in the production bundle. oj answers that specifier with its own module (which stashes a Worker's bindings before Start's handler runs); the module had only the default export, where the package's `dist/default-entry/esm/server.js` also exports `createServerEntry`, so every route answered 500 with "The requested module '@tanstack/react-start/server-entry' does not provide an export named 'createServerEntry'". The default handler also takes the request's options an entry hands it (`handler.fetch(request, { context })`, Start's `(request, opts?)`), so the context reaches server routes, server functions and middleware as it does under Vite; oj's handler took any second argument for a Worker's bindings and called Start's with the request alone. Only a Worker runtime's `fetch(request, env, ctx)` call is read as bindings now; any other call reaches the handler with every argument it was given, as through the package's `createServerEntry`.

## [0.4.10] - 2026-11-11

### Removed

- The experimental on-disk module cache and its `oj dev --enable-cache` / `--no-cache` flags. Compiled modules were never persisted by default, and the TanStack Start dev server never used the cache; keeping it meant keeping a second cache coherent with the HMR stamps (see the `--enable-cache` entry below) for a path nothing ran. The in-memory module cache is unchanged, and `.oj-cache` keeps the other caches (the dep pre-bundle, the Start bundle, the config extraction). An `oj dev` invocation that passed either flag now fails to parse.

### Fixed

- TanStack Start dev: a JSON import reaches an open page through a hot update with the JSON's current value. A component edited to import a JSON file (`import photo from "./photo.json"`, then `photo.url`), or a JSON file edited in place, crashed the page inside the hot patch with "Cannot read properties of undefined (reading 'url')" (or `.filter` for an array), while a fresh load rendered fine. The Start bundles now turn a JSON module into a JavaScript one with named exports and a default, as Vite's json plugin does (plugins/json.ts, rolldown's `builtin:vite-json`), before the bundler links it. Rolldown makes the same exports of a JSON module in its link stage, but a hot update renders a module from the file as scanned, so a JSON module edited or imported for the first time reached the page as a bare expression with no exports.

  - The projects are every `tsconfig.json` and `jsconfig.json` between the importer and the workspace root, with their references. Within a directory they go in `localeCompare` order, and node_modules is skipped.
  - The project whose `include` holds the importer maps it. Only TypeScript importers count, unless `allowJs` is set or the project is a jsconfig.
  - Patterns go `@/*` before an exact key, and every `*` captures. A mapped path goes through `resolve.alias` again. `baseUrl` is tried after `paths`, and a `.json` the import did not name is not taken from it.
  - A declaration-file answer is no answer.
  - The plugin's own options, read from the Vite config where they are literal: `projects` loads only those tsconfigs, `root` moves the project and workspace roots, `projectDiscovery: "lazy"` walks every ancestor, `configNames` names the files, and `loose` (or an `importerFilter` function) takes any importer.
  - An `include` or `exclude` a tsconfig inherits through `extends` stays relative to the config that declares it, as tsconfck reads it.

Only an import a `paths` pattern or `baseUrl` actually maps is taken from the bundler, which keeps its own conditions and import kinds for the rest. Editing any JSON file in dev (a tsconfig reached through `extends` included) takes effect without a restart.

So `{ "@/integrations/supabase/client": "./src/appBackend.ts", "@": "./src" }` sent the client import to the file `@` or tsconfig `paths` gave it, not the one written for it. The dependency scan follows the same order, so it no longer crawls the declaration file and finds the app's dependencies late.
- An environment's own `resolve.alias` is ignored, as in Vite 8: every environment resolves with the top-level list.
- In TanStack Start dev, a server render no longer fails with "require is not defined" when it imports a dependency like turndown, whose `module` build calls `require` (a build meant for a bundler) while its `main` is CommonJS. oj loads a dependency's `module` entry on the server, where Vite loads the file its module runner resolves for an external: `main` only, the external conditions, `resolve.dedupe`. - Stopping the dev server now closes it the way Vite does before sweeping plugin children: the shutdown handler first runs the plugin host's `closeDevServer`, awaiting the `server.close()` that plugins wrap to dispose runtimes they started (`@cloudflare/vite-plugin`'s workerd), then `buildEnd` and `closeBundle`, all inside the existing 5 s bound, which now logs when it runs out. The handler listens on held `deno_signals` streams, so the embedded engine's default signal action can no longer kill the process mid-close (signal-exit, bundled by rolldown's watch module, re-raises SIGTERM on its own pid after the first signal); plugins' own signal listeners still receive the first signal, and the child sweep stays the last word either way.

- The persistent V8 code cache no longer grows without bound. Loading a TS config imports its bundle under a fresh one-shot name every boot (Vite's `.timestamp-<ms>-<hash>.mjs`, oj's fallback `oj-vite-config-<pid>-<rand>.tmp.mjs`), and each name keyed a new, permanently unreachable entry; both shapes now share one stable key, so an unchanged config hits across boots and an edited one overwrites in place. Boot hygiene also prunes the oldest entries once the directory passes a budget (`OJ_CODE_CACHE_MAX_BYTES`, 128 MiB default, `0` disables) and removes dead generation directories left behind by V8 upgrades, whose bytecode can never load again.

## [0.2.19] - 2026-10-08

### Fixed

- Editing a file that a plugin's `resolveId` answers for (a framework's generated file, an alias target) now hot-updates. Such files were compiled by the plugin route itself, never watched and absent from the module graph, so saving them changed nothing until a manual reload; a resolved id naming a plain app file now goes through the normal module pipeline, which still asks the plugin's `load` before reading the disk and runs the transform hooks, as Vite does for every real file. Module-graph nodes in the plugin host also carry the module's served URL (root-relative, or `/@fs` outside the root) instead of its filesystem path, so HMR updates built from them name URLs the browser actually imported, and `urlToModuleMap`/`getModuleByUrl` answer by that URL as in Vite.
- Plugin-spawned children (a Cloudflare plugin's workerd, a framework's sidecar) no longer outlive the dev server. The shutdown sweep now covers every path that used to strand them: the start and ssr serve modes install the same shutdown handler as plain dev (they exited on a bare signal before); the embedded engine's own signal handling, which terminates the process before any parked shutdown task can run, sweeps children on its exit path too; and the handler is installed before boot begins, as Vite installs its SIGTERM listener inside `createServer` before any `configureServer` hook can spawn, so a signal that lands mid-boot still sweeps. Against SIGKILL, where no handler runs at all (an OOM kill, a supervisor escalating after a grace period), the child registry is persisted per server process with pid plus kernel start-time identities; the next boot reaps the previous server's still-identified children before any engine spawns, the way Bazel- and Gradle-style daemon registries recover, and never signals a recycled pid.

The serving gate checks the request's canonical path, but the allow-list entry made from the resolved path was stored raw only; those inserts now store the raw and canonical forms like every other allow-root, so the gate's ancestor check matches.

## [0.2.17] - 2026-10-08

### Fixed

- `fs.watch` scales to thousands of watchers (a plugin watching each file of a large build-output tree used to wedge the plugin host before the server ever listened). Three independent costs made it quadratic, and each now follows what Node/libuv and chokidar do on the same APIs: matching runs on its own dispatch thread, so the notify backend thread only forwards events and `fs.watch` registration can never stall behind matching (libuv does no per-handle work on its watcher threads); an event visits only the watchers indexed on its path, an ancestor of it, or the same file, instead of every watcher by opening files (libuv filters its shared FSEvents stream per handle the same way); and on macOS, where notify rebuilds its FSEvents stream on every `watch()` call, a watched file registers its parent directory, deduplicated, exactly as chokidar's fsevents handler does, so a directory of watched files costs one registration.

### Changed

- Start dev serves the client bundle with an ETag from each chunk's content hash (a reload revalidates to a 304 instead of re-downloading), `immutable` caching for its hashed chunks, and gzip for browsers that accept it. On a 2000-component app the entry goes from 2.7 MB to about 340 KB on the wire.
- The dev server's module 304s follow `If-None-Match` the way HTTP defines it: a list of tags, `*`, and weak (`W/`) tags all match, where only the exact single tag did before.
- Dependency pre-bundling runs on rolldown, the only engine, as in Vite 8 (which removed its esbuild optimizer): a Vite 8 app pre-bundles with the rolldown its vite declares, any other app with the rolldown vendored with oj, then one it installs itself. Vite 8 apps ship no esbuild, so until now their deps were never pre-bundled and every dependency file was its own request. `optimizeDeps.esbuildOptions` stays honored the way Vite 8 maps it onto the rolldown run.
- Dependency discovery is on by default, as in Vite: oj crawls the app from its entries and pre-bundles every dependency it imports. `optimizeDeps.noDiscovery: true` limits pre-bundling to `optimizeDeps.include`. The default entries follow Vite's computeEntries: `optimizeDeps.entries`, else the config's `build.rollupOptions.input`, else every html file under the root (node_modules and `build.outDir` ignored), with `<script type="module">` srcs and inline module scripts both scanned; before, only root `index.html` script srcs were. `import.meta.glob` patterns are expanded during the scan, as Vite's scanner does, so a dependency imported only by a glob-matched module is still pre-bundled.
- With a rolldown pre-bundle, the dependency scan resolves imports through the app's plugins first (with `scan: true`, like Vite), so an import only a plugin can resolve is still discovered, and `optimizeDeps.rolldownOptions` applies to the scan and the bundle as in Vite (its `plugins` join the scan). Dependency bundles define `process.env.NODE_ENV` as `NODE_ENV || mode`, like Vite, instead of always `development`. The scan runs under the optimizer's budget (`OJ_OPTIMIZE_TIMEOUT`, 120 s default), not the per-plugin-hook one, and the include list resolves through the plugins even with `noDiscovery`.
- What a rolldown pre-bundle leaves external is written as the URL oj serves it at: a dependency's CSS and assets, `optimizeDeps.exclude`d packages, and `new URL("./file", import.meta.url)` references. Node builtins become Vite's browser-external stub and a missing optional peer dependency throws only when evaluated, both inside the bundle. A `require()` of an excluded package goes through an import facade, as in Vite, and a dependency entry that ships JSX in a `.js` file switches the bundle to parse `.js` as JSX instead of failing it. The pre-bundle cache is keyed on the app's plugin names too, since the scan resolves through them. A bare import that resolves to a non-JS file (a css-main package) is externalized by its resolved type, the externalized asset list matches Vite's (`.vtt`, `.pdf`, `.txt`, ...), the `import.meta.url` rewrite skips matches inside strings and comments and honors `/* @vite-ignore */`, and an `optimizeDeps.include` entry that does not resolve is dropped with a warning.
- Runtime dep discovery, as in Vite: a bare import the pre-bundle missed (a package installed mid-session, or a module only reachable through a runtime-built `import()`) registers when the dev server first serves it and is rewritten to its future optimized URL immediately; requests for that URL wait for the debounced re-optimization to commit. A commit that left previously served entries byte-identical keeps every URL valid and reloads nothing; one that changed them moves all URLs and compile caches to a bumped version and reloads the page once, and a request still carrying the old version gets a 504, like Vite's outdated-dep handling. Discoveries persist in the manifest for the next boot. When no rolldown is found at all, discovery turns itself off and every dependency serves per-file, as a bundler-less app always did.

### Removed

- `OJ_OPTIMIZE_SCAN`. Discovery is the default; `optimizeDeps.noDiscovery` turns it off.

## [0.1.24] - 2026-09-07

### Fixed
- A restarted SSR-container process now RECONNECTS and recovers instead of degrading forever. 0.1.23 stopped the `EPIPE` crash by marking the plugin bridge "down" on a write failure, but "down" was permanent: a container that restarted mid-session (a supervisor relaunch) left the bridge dead for the rest of the process, so every later render served oj's own resolve/load fallback with no plugin pipeline. The bridge now reconnects to a restarted container over the recreated fifos and retries the call once, so a transient restart returns the real result; if no container comes back within the reconnect window (`OJ_SSR_BRIDGE_RECONNECT_MS`, default 5s) the call returns null and reports "down", and "down" is no longer terminal, so a later call re-probes and heals a container that comes back afterward. Every fifo open on the recovery path is non-blocking, so a container that dies mid-reconnect can no longer hang the synchronous render thread on `openSync`, and the first re-probe of a still-dead container fast-fails instead of stalling for the full window.
- A stale or partial reply frame left in the reply fifo by a dying container can no longer misframe the next call. On reconnect the bridge drains any residual bytes before retrying, a reply-length cap rejects a garbage length header (which would otherwise drive a multi-gigabyte buffer allocation) as a stream desync, and a malformed reply is recovered like a container death (reconnect and retry) rather than thrown as a hard SSR error.
- The Start SSR loader no longer persists an under-transformed module when the container is momentarily gone. A `down` container skips the plugin `load`/`transformUserCode` steps, so the loader must not cache that render under the same key a healthy render uses; the outer `ssr-loader` disk cache and the unclaimed-`.js` marker are now both guarded by the bridge's `down()` signal (matching the guard already on the inner transform caches), so a one-off container blip can no longer freeze a plugin-untransformed or falsely-unclaimed module on disk across restarts.

## [0.1.23] - 2026-09-07

### Fixed
- A dead SSR-container process no longer crashes the whole loader/dev process. The Start SSR plugin bridge talks to the plugin-host container over named-pipe request/reply fds; the reply side already degrades to "down" when the container goes away, but the request write (`writeSync(reqFd, ...)`) was unguarded, so when the container exited or was restarted mid-session the next write threw an uncaught `EPIPE` (broken pipe) that took down the loader (surfacing as a 500 with a dead page). Pre-init calls now wait on the init signal first and write only once the host is provably reading (with the per-call timeout additionally covering the write itself, as a belt). Each pre-init call keeps its OWN full wait window (`OJ_PLUGIN_TIMEOUT` on a lazily spawned host): an earlier call's expired window is evidence of a slow boot, not a wedge, so it never fails a later call early — a call arriving late into a healthy slow init is served the moment init lands — while a truly wedged host degrades each caller like a slow hook (one window apiece, zero bytes written) and only the host actually dying fails calls fast.
- An `oj.config.json` `ssr.resolve` block now merges per-key with the extractor's (oj's sub-keys win, missing ones fill in), so an oj-side `externalConditions` no longer drops the extracted workerd `conditions`; a non-object oj-side `ssr` (or `ssr.resolve`) value warns and adopts the extractor's block instead of silently dropping `runnerBacked`.
- The plugin host's config-hook merge now matches Vite's `mergeConfigRecursively` where it did not: a hook returning `key: null` no longer clobbers a set value, `true` on either side of ssr/resolve `noExternal`/`external` wins over lists, and only PLAIN objects merge recursively (Vite's `isObject`) — two `RegExp` values (an `ssr.noExternal` regex, say) now take the later one instead of being spread key-by-key into an empty `{}`.
- A Vite-shaped `resolve.mainFields` list (Vite's defaults omit `"main"` because its resolvePackageEntry always falls back to `pkg.main` afterwards) made a package whose ONLY entry is `main` unresolvable once adopted from the config — e.g. a linked workspace package with a TS `main` and no index file. oj's resolver now appends the same `main` fallback (last, never outranking the configured fields), mirroring Vite's `entryPoint ||= data.main` — and the production build's rolldown resolver and the dependency prebundle apply the identical append, so an import that resolves in dev can no longer fail the build or the optimizer under the same list.
- A module that both reads `import.meta.hot` itself AND is a React refresh boundary (a TanStack route file: the router plugin injects its own `import.meta.hot` handler) was served with the hot-context banner twice — the prepended banner plus the refresh glue's own import — and two import bindings named `__oj_createHotContext` in one module scope are a SyntaxError that killed the module in the browser. The refresh glue now reuses a predefined hot context instead of re-declaring it, as Vite's refresh footer reuses the import-analysis banner.
- The Node SSR paths could resolve a package's `browser` conditional export and execute DOM code server-side (`ReferenceError: document is not defined` at module scope, e.g. `decode-named-character-reference`'s `index.dom.js`, failing every SSR render). Two halves. First, on an app whose ssr environment carries a workerd condition set (the Cloudflare plugin's `workerd, worker, module, browser`), `resolve.conditions` never saw it: the resolved ssr conditions travel on the extractor's `ssr.resolve` sugar, and the lookup fell through to the top-level `resolve.conditions` — which a resolved Vite config fills with the *client* defaults, a browser-bearing list that steered every noExternal/linked resolution into browser builds. `resolve.conditions` now falls back environment → `ssr.resolve` sugar → top level, exactly like `externalConditions` already did. Second, conditions never cross runtimes (Vite's model: an environment's conditions steer resolution only for code that executes in that environment's own runtime). The config extractor now marks the ssr environment "runner-backed" (`ssr.runnerBacked`) from Vite's own declaration mechanism — the raw config, or a plugin's `config` hook return merged the way Vite's `resolveConfig` merges them (before Vite default-fills every environment's factory), declares `environments.<name>.dev.createEnvironment`; the same declaration gates the plugin host's `buildEnvironments` — and every Node-executing consumer (the Start loader's env plumbing, the plain unbundled SSR resolver) then takes Vite's Node server semantics instead of the foreign runtime's list: `DEFAULT_SERVER_CONDITIONS` (`module`, `node`, dev/prod) plus the user's RAW top-level `resolve.conditions` (published as `rawResolve`; the resolved top-level list is the client environment's and never crosses), and `DEFAULT_EXTERNAL_CONDITIONS` (`node`, `module-sync`) unless the raw top-level `resolve.externalConditions` replaces them, as a user list does in Vite. A non-runner-backed environment's list passes verbatim, no stripping: an explicit user `browser` (happy-dom-style Node SSR) stays honored, as Vite honors user conditions. The generic SSR production bundle (`oj build`'s Node-target server output) applies the same source selection instead of inheriting a workerd-shaped list verbatim, and the stale "ssr.resolve is not applied" config warning now names only the genuinely-inert subkeys (`conditions`/`externalConditions` are applied).
- On a slow boot (a large plugin fleet, a Miniflare boot inside `configureServer`) every boot-time plugin RPC burned its own 20 s timeout and permanently snapshotted wrong defaults — config()-hook defines and env mutations were dropped, hook gates defaulted, and on Cloudflare apps `getServeInfo` failed so the worker path silently never activated (no `plugin middleware: forwarding unmatched requests` line; every document degraded to the Node SSR runner for the whole session). The host answers RPCs only after its top-level init, and its init-complete moment is now observable — it pushes `{ ojServeInfo }` the instant init finishes — so RPC sends are gated on an "initialized" state derived from that push or the first reply: before init, a call waits (bounded by `OJ_PLUGIN_INIT_TIMEOUT`, default 300 s, with a "plugin host still initializing (Ns)…" progress line every 30 s) instead of racing its per-call timeout against the boot; after init the 20 s per-call timeout applies unchanged, and fast boots behave byte-identically. Should a host still outlive the init deadline, activation is now a proper transition rather than a flag flip: the middleware state is one atomically packed snapshot (readers can never see the port without the serve mode), the flip synchronously re-arms the Start fallback runner (`runner_dirty`) before it becomes visible — closing the window where an edit racing the flip took neither reload path — and one catch-up resync (`{"resync":true}` on `/__oj_invalidate`) invalidates every runner-backed environment's whole module graph and full-reloads it, so edits made during the degraded window are never lost — "resynced" is logged only when the host reports the resync actually executed (a transient enqueue failure is retried with backoff; a resync that never lands or never runs warns that degraded-window edits may be stale instead of claiming success). The warning also stopped guessing from config text (the raw `@cloudflare/vite-plugin` substring search false-positived on commented-out imports): oj warns only when the host never finished initializing within the deadline, and the host itself — which knows whether a runner-declaring plugin is active — warns when one is present but no environment came up. The init gate's reach is scoped per spawn: only the boot-time host (whose snapshot RPCs boot correctness depends on) waits out the long deadline, while a lazily spawned host (the SSR environment host, created on the first SSR request) bounds its init wait by the ordinary 20 s per-call timeout — anchored to EACH call's own start (a spawn-anchored bound gave calls arriving after spawn + 20 s during a pending init a zero-length window: instant failure), so a wedged init degrades like a slow hook instead of freezing the watcher thread's HMR dispatch and browser-facing SSR transforms for minutes. The host also signals init-complete explicitly in BOTH modes (`{ ojInit: true }`, once its RPC listener is up): build mode has no serve-info push, and previously a hanging first hook there waited out the whole init deadline blamed on initialization. The Start prewarm's serve-info wait is bounded by the same `OJ_PLUGIN_INIT_TIMEOUT` knob instead of a second hardcoded number, an activation landing between server build and the Start hook's registration is caught up inline (the fallback runner is still marked dirty), and a plugin host that dies before ever initializing is reported ("plugin host exited before initializing") and released instead of being pinned by its own watcher task forever.
- The plugin host's control plane shared a raw stdout line protocol with plugin code: a plugin's unterminated partial write could splice the one-shot `{ ojServeInfo }` push (parse fails, silently dropped, never retried), and any plugin output — including attacker-controlled content a plugin echoes — that happened to spell a protocol line could forge a push or an RPC reply. Every oj protocol line (RPC replies, ctx-RPC requests, and the `ojServeInfo`/`ojServer`/`ojWs` pushes) is now framed: a leading newline terminates any dangling partial line, and a per-session random token (`OJ_CONTROL_TOKEN`, minted at spawn) prefixes the line — the reader ignores unframed lines entirely, so plugin prints can never be parsed as protocol (forging requires reading the host's env: the same trust domain as running plugin code). The serve-info push is additionally re-sent once a second until oj ACKs it, so even a spliced copy heals.

## [0.1.17] - 2026-09-05

### Changed
- Cloudflare dev (`@cloudflare/vite-plugin`): on a source edit the worker environments no longer get a blanket `full-reload` that made the module runner re-walk the whole server graph (the next document after an edit took several times what `vite dev` takes on a large TanStack Start app). oj now mirrors Vite's HMR propagation over each environment's module graph (plugin `hotUpdate` hooks included) and sends targeted `{type:"update"}` payloads to the nearest accept boundary (the plugin's worker entry self-accepts), falling back to `full-reload` where Vite does (a propagation dead end, a graph without the walk API) and sending Vite's `{type:"error"}` payload when a `hotUpdate` hook throws. Changes travel with Vite's watcher event types: a delete goes through `moduleGraph.onFileDelete`, a created file retries the modules whose imports previously failed to resolve, `pluginContainer.watchChange` runs with the matching event, legacy `handleHotUpdate` plugins are dispatched for the client environment, and a hook's `read()` retries a truncated write as Vite's `readModifiedFile` does.
- Cloudflare dev: the Node SSR runner becomes a cold fallback when the worker environments serve the documents — the boot prewarm render is skipped and the per-edit runner reload is replaced by a lazy reload right before the runner's next actual use. Server environments get `dev.preTransformRequests` enabled unless the config sets it, so the module runner's serial import walk is pipelined by import-analysis pre-warming. Environments are created and initialized in parallel, as Vite's `createServer` does, and `OJ_BOOT_PHASES` marks the second `resolveConfig` and each environment's creation and init. Apps without the plugin are untouched.

### Fixed

- `resolve.externalConditions` set in a `vite.config.*` was silently dropped: the extractor only carried `extensions`/`mainFields`/`conditions`, so the option worked from `oj.config.json` alone while externalized SSR deps fell back to the default conditions. It is now extracted top-level, through Vite's `ssr.resolve` sugar and the `environments.ssr.resolve` spelling (the environment wins), and looked up with the same precedence.
- The SSR loader's persistent caches were keyed without `resolve.externalConditions` and `ssr.noExternal`/`external`, so editing either and restarting replayed the previous run's resolutions; `oj.config.json` was also missing from the cache's base inputs. All three now invalidate the cache.
- `browser` was stripped from the user's ssr `resolve.conditions` for every app; it is now dropped only from a workerd-shaped list (one that also names `workerd`, the Cloudflare plugin's set, which must not pick browser builds in the Node loader) and an explicit user `browser` condition is honored, as Vite honors user conditions.
- A metadata-only file event on a never-seen path was dropped, so the first `touch` of a file per session did nothing (a second worked). With no recorded baseline, a fresh modification time now counts as a change; an old one is still the access-time noise the filter exists to ignore.
- Config evaluation raced itself at boot: the route tree, the server-fn resolver, the config extractor and the plugin host all bundle `vite.config.ts` concurrently, and the extractor script plus the bundled config shared fixed filenames, so one process could truncate a file another was importing (`could not extract vite.config values`, `failed to load config`, an extractor that "wrote nothing at all"). The script now lands by atomic rename, every bundled config gets a per-process temp name that is removed after import, and the extractor writes its JSON to a per-call result file instead of stdout, which plugin code (a route generator's warnings) could pollute.
- Cloudflare dev: worker-served documents did not get the live-reload client injected, so a tab on a plugin-served app never reloaded on edits. The plugin middleware's HTML responses now get the same tail injection as runner-served documents (responses with a `content-encoding` are left untouched, on every injection path).
- A document requested milliseconds after a save could be rendered from stale worker modules: the watcher now invalidates the worker environments on the first raw file event, before its 50 ms settle window and the rebuild, and again with the settled batch. The invalidation endpoint also answers only after the module graphs are updated.
- TanStack Start dev: a second edit landing while the first edit's client rebundle was in flight queued behind it (the watcher thread sat inside the rebundle), so interim documents served the previous version and fresh content appeared only seconds after the second edit. The watcher thread now only receives, classifies, settles and hands batches off, the way Vite's watcher callbacks run per event; worker invalidation fires promptly per batch on the async runtime, and the client rebundle plus route-tree/server-fn regeneration run in a coalescing worker (batches landing mid-run merge into at most one pending rerun). The run keeps the inline loop's ordering: a regenerated route tree or server-fn resolver gets its own worker invalidate after regen (the watcher deliberately never forwards those files), the lazy runner's dirty flag is re-armed post-regen so a fallback request that consumed it mid-run cannot hold stale generated files, and the non-lazy runner reloads only after regen, all before the browser reload, which still fires once per completed rebundle, after that batch's settled invalidation.
- Cloudflare dev: the early (pre-settle) and settled invalidation sends for one write usually carry the same change, so the plugin host replayed the watcher event and the whole `hotUpdate` pipeline (hooks, targeted updates, the runner's chain re-fetch) twice per edit. The host now skips a change whose type and file content hash match the last processed one, mirroring Vite's single chokidar event per FS change: identical consecutive content is the early/settled pair, while a write landing inside the settle window, a revert, and same-mtime distinct writes all still process (a read error also always processes). A "create" for a file a runner environment's module graph already knows is an atomic save's recreate half and is handled as an update, closing the update-then-create double pass and the phantom watcher "add".
- The dev watchers treated attribute-only file events as changes. On Linux the first read of a file after it was written updates its access time, which inotify reports as an attribute change, so a rebuild that reads every source file (the TanStack Start client bundle does) looked like an edit of every source file and triggered another rebuild until the access times settled, with the HMR gate filling up with phantom changes. Both watchers now apply chokidar's rule: a change is a data change or a moved modification time; an attribute event with an unchanged mtime (or on a file never seen before) is ignored, and a `touch` still counts.

When `@cloudflare/vite-plugin` is present, the Node plugin host loads the app's installed Vite (oj takes no Vite dependency of its own), builds real `DevEnvironment`s via each environment's `dev.createEnvironment`, and lets the plugin drive Miniflare/workerd; documents and server functions both run in the worker with real vars/bindings, exactly as `vite dev` runs it. ## [0.1.9] - 2026-08-31

### Added
- Experimental foundation for running Cloudflare (workerd) SSR natively, with no Node, Miniflare, or Vite plugin. `oj_server::workerd` locates the `workerd` binary, generates its Cap'n Proto text config (a worker with a socket, a module-fallback address, and var/service bindings), and answers workerd's module-fallback requests with TS/JSX-stripped ESM served from oj's compiler. A bare `node_modules` import is resolved through oj's resolver (under workerd/worker export conditions) and answered with a 301 redirect to its absolute path, so a worker's whole module graph is served on demand; oj's Start module aliases (for example `tanstack-start-manifest:v`) redirect the same way to their target files, and a served module's `#`-subpath alias imports (which workerd resolves through package `imports` and never sends to the fallback) are rewritten to their target's absolute path before the module leaves the fallback. A CommonJS `node_modules` module (a `.cjs`, or a `.js` with no ES module syntax) is wrapped into ESM so workerd's ES module loader can evaluate it: its `require()` calls resolve to fallback-served paths (or a `node:` builtin under `nodejs_compat`) and `module.exports` becomes the default and named exports. The project's `wrangler.jsonc`/`.json`/`.toml` is parsed (`oj_server::wrangler`) for the worker's `compatibility_date`, `compatibility_flags` (such as `nodejs_compat`), `vars`, and service bindings, with `.dev.vars` overriding, and those feed the generated config so worker bindings resolve locally. The fallback resolves the specifier classes a real app produces: a directory import redirects to its `index` file (so the module's own relative imports resolve against the right directory), a `#`-subpath import resolves through the nearest `package.json` `imports` map, and a `.json` import is served as an ESM default export. A module the Rust tiers cannot resolve (a `virtual:` module synthesized by a Vite plugin, such as the TanStack router plugin's) is proxied to an optional plugin-loader endpoint (`workerd-plugin-loader.mjs`, which runs oj's JS plugin container) and returns native ESM, so plugin virtuals resolve without teaching Rust every plugin. On a Cloudflare project with a `workerd` binary present, `oj dev` now spawns a workerd session and the plugin loader, and routes document requests to the worker (falling back to the Node SSR runner when workerd or the loader is unavailable). `oj_server::workerd_dev::spawn` orchestrates a live session: it starts the module-fallback service, picks the worker's HTTP socket, writes the config, and spawns `workerd serve`, killing it on drop. End-to-end tests render a TypeScript route (including a `node_modules` import, and a `:`-scheme module alias) inside real workerd. Detection is gated on a Cloudflare project (`wrangler.jsonc`/`.json`/`.toml`), and `oj dev` renders a real TanStack Start Cloudflare app end-to-end. A source edit is reflected live: the file watcher evicts the changed module from an in-memory transform cache (keyed by path and modification time, self-invalidating) and reloads the running worker's isolate, so the next render serves the new output without restarting `oj dev`. The transform cache is shared between the module-fallback service and the watcher, so every render after the first reuses already-compiled modules instead of recompiling the graph.
- `oj_compiler::ssr::ssr_transform` — a Vite-compatible SSR / module-runner transform. It rewrites ES module syntax into the `__vite_ssr_*` runtime contract a Vite module runner evaluates: static imports become `await __vite_ssr_import__(...)` with references rewritten to live member access, exports become `__vite_ssr_exportName__` getters, `export *` becomes `__vite_ssr_exportAll__`, dynamic `import()` becomes `__vite_ssr_dynamic_import__`, and `import.meta` becomes `__vite_ssr_import_meta__`. Reference rewriting is scope-correct through oxc symbol resolution (shadowed locals are left alone), and live bindings are preserved. Type-only imports and exports (`import type`, `import { type X }`, `export type { … }`, `export type *`, `export { type X }`) are dropped rather than emitted as runtime imports. `ssr_transform_module` composes it with oj's existing TS/JSX strip so a `.ts`/`.tsx` module becomes runner-ready in one call. A companion `ssr-fetch-module.mjs` implements the Vite `vite:invoke`/`fetchModule` RPC responder (resolve → externalize routing → load → transform, returning a Vite `FetchResult`), and the dev server can serve runner-transformed modules over `/@ssr-module?...&runner=1`. Together these are the module-transform and fetch-module halves a Vite module runner needs, so oj can serve runner-transformed modules to an out-of-process runner (for example a workerd/Cloudflare dev runtime).

## [0.1.8] - 2026-08-29

### Fixed
- `import.meta.glob` with a TypeScript type argument is now expanded in the TanStack Start SSR path even when the type argument is nested (`import.meta.glob<Record<string, unknown>>(...)`) or an object literal (`import.meta.glob<{ default: T }>(...)`). The Start transform located the call with a regex that stopped at the first `>`, so a nested generic slipped through unrewritten and reached the SSR runtime as a real `import.meta.glob(...)` call, throwing `TypeError: (intermediate value).glob is not a function` and 500ing the route. The detector now skips a balanced, string-aware type argument before the call, matching the AST-based compiler path.

## [0.1.7] - 2026-08-29

### Added
- `server.hmr: false` disables HMR, matching Vite: file edits stop broadcasting reloads (the page holds until a manual refresh) while the dev server and plugin WebSocket keep running. Honored from both a `vite.config` and an `oj.config`.

### Fixed
- `import.meta.glob` is now expanded in `.jsx` and plain `.js`/`.mjs` modules in the TanStack Start SSR path, not only `.ts`/`.tsx`. Previously a `.jsx` route/component (or an unclaimed on-disk `.js`) that used `import.meta.glob` reached the SSR runtime untransformed and threw `TypeError: (intermediate value).glob is not a function`, 500ing the route. The dev SSR loader and both the SSR-server and client production builds now run the glob transform for the full JS/TS family.
- oj now accepts the Vite HMR WebSocket. A Vite HMR client dials the origin root with the `vite-hmr` subprotocol, but oj served its HMR socket only at `/__ws`, so that dial never upgraded and the client could not connect. oj now intercepts a `vite-hmr` upgrade on any path (matching Vite's subprotocol-based dispatch), echoes the subprotocol, and sends `{ "type": "connected" }` first, so the client connects and receives oj's existing Vite-shaped reload frames. The `vite-ping` liveness-probe subprotocol is accepted and closed immediately, as Vite does. This runs entirely on oj's native Rust WebSocket path, with no Node plugin host on the HMR path.

## [0.1.5] - 2026-08-26

### Added
- `resolve.extensions`, `resolve.mainFields`, and `resolve.preserveSymlinks` are now honored by the resolver.
- `envPrefix` accepts an array of prefixes (`string | string[]`).
- `css.preprocessorOptions.scss.additionalData` (and `sass`) injects a preamble before Sass compilation.
- `server.strictPort` is honored; by default the dev and preview servers move to the next free port when the chosen one is busy (Vite parity), and error only when `strictPort` is set.
- `optimizeDeps.esbuildOptions` (`define`, `target`, `loader`, `jsx*`, `mainFields`, `conditions`, `keepNames`, ...) is now applied to dependency pre-bundling instead of being ignored.
- `?worker&inline` emits an inline Blob worker (with a `data:` URI fallback) in bundle mode, matching Vite; in dev it serves a working module worker instead of a broken data URI.
- Plugin `handleHotUpdate` now receives the full Vite `HmrContext` (`file`, `timestamp`, `type`, `modules`, `read()`) and its returned module list is honored to narrow (or, when empty, suppress) the update, folded across plugins as in Vite.
- `build.rollupOptions`/`rolldownOptions.input` is honored (string, array, or `{ name: path }` object), so multi-page projects and projects without a root `index.html` build. HTML entries under nested directories are emitted at their root-relative path and their page-relative `<script>` sources are resolved against the page, matching Vite's `input` resolution.
- Plugins can call `this.emitFile({ type: "chunk", id })` during `buildStart` or `transform`; the chunk is bundled as a build root and `this.getFileName(referenceId)` resolves to its final hashed name in `generateBundle`. Plugin `buildStart` now runs as a rolldown build hook and receives an `options` object with `input` (the emit-chunk mechanism CRXJS-style plugins use to emit their manifest root, content scripts, and pages).
- The `generateBundle` bundle now exposes the full Rollup chunk shape (`facadeModuleId`, `moduleIds`, `modules`, `imports`, `dynamicImports`, `exports`, `isDynamicEntry`, `sourcemapFileName`; assets carry `name`/`names`), and plugins can rename an output by setting its `fileName` and delete an output with `delete bundle[key]` (used by CRXJS to rename pages and drop its manifest JS chunk).
- A plugin emitting an HTML page as a chunk (`this.emitFile({ type: "chunk", id: "...page.html" })`) now gets the Vite HTML treatment: the page's `<script type=module>` are bundled as entries, the processed page is written at its root-relative output path, and `getFileName(referenceId)` resolves to that page path (how CRXJS emits the extension's popup/options pages from its manifest).

### Added
- oj provides a `vite:css-post` plugin shim during the build. Plugins that look one up in `config.plugins` and hand it their generated CSS in `renderChunk` (UnoCSS, and similar) now have that CSS folded into the build's stylesheet output. `renderChunk` hooks also receive the full chunk shape (`modules`, `moduleIds`, `facadeModuleId`, ...) and a `NormalizedOutputOptions`-style `options` with a resolved `dir`, and a plugin-served virtual `.css` module is kept in the graph as a side-effect stub so those hooks can find it.
- The Vite build manifest is now present in the `generateBundle` bundle as a `.vite/manifest.json` asset, so plugins that read it there (for example `@crxjs`'s web-accessible-resources) can find it.

### Changed
- Plugin `transform` hooks now run on CSS and preprocessor (`.css`/`.scss`/`.less`/`.stylus`) sources during the build before oj compiles them, matching Vite where CSS is a real module in the graph. This lets directive transformers such as UnoCSS's `@apply`/`@unocss-include` resolve before Sass/lightningcss run.
- Plugin `transform` sourcemaps are now composed with oj's own transform map, so dev sourcemaps trace back to the original source through plugins that rewrite code.
- CSS imported with `?inline` returns the compiled CSS string instead of a base64 `data:` URI.
- Dev-served CSS rewrites relative `url()` and `@import` references to server-absolute paths so injected styles resolve them.

### Fixed
- `config.publicDir` is now resolved to an absolute path in `configResolved` (default `<root>/public`, Vite parity), so plugins that read it to locate assets (for example `@crxjs` loading a manifest's icons/locales) find them instead of seeing `undefined`.
- The `config`/`configResolved` hooks now see only the command-applicable plugins in `config.plugins` (serve-only plugins are excluded from a build, matching Vite), and `config.plugins` is no longer duplicated by config hooks that return their own `plugins` (the array is pinned across the config-hook merge). A plugin's `generateBundle` error is now surfaced instead of silently swallowed. Together these let `@crxjs`'s build-time manifest plugins (`transformCrxManifest`/`renderCrxManifest` fan-outs) run once and without a serve-only `crx:hmr` crashing them.
- Sass now resolves a relative dotted `@use`/`@forward`/`@import` (e.g. `@use 'colors.module.scss'`) made from inside another dotted `.module.scss` stylesheet: the nested import resolves against the imported file's real directory instead of the phantom directory grass sees a dotted basename through, so cross-directory CSS-modules stylesheets compile.
- Plugin `configResolved` now runs before `applyToEnvironment`, matching Vite; plugins that populate state in `configResolved` and read it from `applyToEnvironment` (for example `@tanstack/router-plugin`) no longer crash the plugin host, and a throwing `applyToEnvironment` keeps the plugin active instead of failing config load ([#37](https://github.com/raphamorim/oj/issues/37)).
- The `config` and `configResolved` hooks now receive `config.plugins` (the flat plugin array) and a defaulted `config.build` (`outDir`, `assetsDir`, `rollupOptions`, ...), matching Vite's resolved config. Plugins that read these in their config hooks (`@crxjs/vite-plugin` reads `config.plugins`; UnoCSS resolves `config.build.outDir`) no longer throw and get skipped.
- A module returned from a plugin `load` hook in the build is now typed from its id's extension (`.jsx`/`.tsx`/`.ts`/`.json`) instead of always JavaScript, matching how Vite derives the transform language from the id. Virtual modules like unplugin-icons' `~icons/*.jsx` are parsed as JSX again instead of failing with "JSX syntax is disabled". Build errors also now render with their source file and location rather than an opaque diagnostic dump.

### Security
- `server.fs.deny` is enforced, and oj blocks `.env`, `.env.*`, `*.crt`, `*.pem`, and `**/.git/**` by default (Vite parity).
